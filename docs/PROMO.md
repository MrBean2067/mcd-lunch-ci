## 一、V2EX「分享创造」

V2EX 反感营销腔，标题要平、正文要讲技术细节，**不要出现"求 star"**。

**标题**
```
[分享创造] 把「中午吃什么」做成了一条 7 阶段 CI 流水线
```

**正文**
```
起因很蠢：我们 8 个人，每天 11:40 开始在群里讨论午饭，讨论到 12:00 还没结论。
最后总是某个人不耐烦了随便点一份，然后另外两个人在工位上念叨"我不想吃这个"。

试过的方案都不行：
- 群里投票 → 每次都是"随便"最多，投完还得再吵一轮
- 让大模型推荐 → 它给的是一个"看起来合理"的套餐，价格不核、忌口不管、
  有人 600 kcal 上限它照给一个 1200 kcal 的，理由是"这家招牌是它"

所以我自己写了一个。核心判断是：这件事不是"推荐"问题，是"决议"问题。

## 它做的是决议，不是推荐

每个人写清三件事：预算、忌口、热量上限。然后：

1. 忌口/热量/预算是**代码里的硬过滤**，不是提示词里的叮嘱。
   模型无权放行过敏原——这条是硬约束，写死在 `Member.violation()` 里。
2. 对每个人算出「在硬约束内他能拿到的所有方案」，按效用排序成阶梯。
3. 用帕累托前沿 + 整数背包 DP 求**总预算内社会福利最优**的那一档。
4. 调 MCD 的 MCP 核价，官方金额和本地求和做对账。
5. 输出三档：推荐 / 省着点 / 极限，附「预算—满意度前沿」曲线。
6. 默认只出预览，加 --confirm 才真下单。付款永远由人扫码。

## 我觉得最有价值的一个输出

大部分人做这类工具，输出是"建议你点 A+B+C"。
我额外输出了这个：

  谁妥协了
    · 老周：拿到 牛肉堡 + 圆筒冰淇淋，满意度 38%；
            他更想吃 巨无霸 + 派 + 可乐（¥43.50），差 ¥23.50
    · Kevin：拿到 麦香鸡 + 圆筒冰淇淋，满意度 70%；差 ¥8.00
    · 小满：拿到 麦香鸡 + 圆筒冰淇淋，满意度 83%；差 ¥3.50

因为团队点餐真正的摩擦不是"选哪个"，是"凭什么是我让步"。
把这个摆到台面上，比给一个"最优解"有用得多——老周看到自己差 ¥23.50，
下次讨论预算的时候就有依据了。

（早期这个字段显示"差 0.24 分效用"，被同事骂了一顿，改成钱了。）

## 几个真实的坑

调 MCP 的过程中踩到的，每个都是"不报错但结果错"的那种：

1. **返回体是「说明文字 + JSON」混合体**。content[].text 前面挂了一段给模型看的
   提示语，直接 json.loads 必炸。得扫文本抠 JSON。
2. **菜单接口不给名称和价格**。query-meals 只返回 {code, tags}。
   名称要 query-meal-detail，价格只能靠 calculate-price 反推。
3. **批量核价会把满减摊到每个商品上**。这是最贵的一个 bug：
   我为了少发请求，把 102 个餐品塞进一次核价，用返回的 subtotal 当单价。
   结果本地算 ¥199.90，官方核价 ¥222.40，差 ¥40，而且不报任何错。
   根因是整单触发了满减，服务端把折扣摊平了。单价必须逐项核。
4. **营养表按餐品名索引，不按 code**，而且缺失值是 null。
   这个坑直接导致一个安全问题：营养缺失时 kcal 算成 0，能轻松通过 600 kcal 上限。
   现在的规则是"证明不了安全就不放行"，报告里这类热量显示"未知"、合计写 "≥3192"。
   缺数据不等于 0 卡，这是整个项目最危险的默认值。
5. **"纯牛奶"含"牛"**，一度被标成牛肉过敏原。用否定前瞻 牛(?!奶|油果) 修掉。
   "麦辣鸡腿汉堡"因为含"鸡腿"被判成小食，改成结构词优先。

## 现在什么状态

- 纯标准库，零第三方依赖，40 个单测（含一条用穷举验证 DP 真的是最优解）
- 无 Token、无网络也能跑：菜单是从真实 MCP 同步下来的快照（102 个餐品 / 57 条实测营养）
  python -m mcd_lunch_ci demo
- 实时链路已和官方核价对上，分毫不差
- 也包成了 WorkBuddy Skill

仓库：https://github.com/MrBean2067/mcd-lunch-ci

顺手写这个是因为年底被这事烦了一个月。有一样困扰的可以试试，觉得没用也欢迎说说
哪一步的设计是多余的。
```

**标题**
```
我把团队午饭做成了 CI 流水线：帕累托前沿 + 整数背包 DP 解多人点餐
```

**摘要（掘金那个 100 字摘要框）**
```
8 人团队点午饭，每天吵 20 分钟。我把它建模成「带硬约束的整数背包 + 社会福利最大化」，
用帕累托前沿压缩候选、DP 求预算内最优解，并输出「谁妥协了、差多少钱」。
附带真实 MCP 联调踩到的 5 个坑（混合文本抠 JSON、批量核价摊折扣差 ¥40）。
```

**正文骨架**（按这个顺序写，掘金读者吃这套）

1. **问题不是推荐，是决议** —— 三分法：满足硬约束 → 压缩候选 → 在预算内最大化总福利
2. **硬约束必须在代码里** —— 为什么不能用提示词做过敏原过滤（给一段 `Member.violation()` 代码）
3. **候选压缩：帕累托前沿** —— 一个人 60 个组合里，只有 5~8 个是非支配的
4. **整数背包 DP** —— 预算按 0.5 元分桶，状态 `(已用分桶, 各成员档位)`；
   用穷举对拍验证（贴 `test_solver.py` 里那段 `itertools.product`）
5. **把效用翻译成人话** —— 从"差 0.24 分效用"到"差 ¥23.50"的取舍
6. **真实联调的 5 个坑** —— 上面 V2EX 正文里那 5 条，逐条给现象 + 根因 + 修法
7. **数据诚信** —— 缺数据不等于 0 卡，为什么这里必须显示"未知"

代码片段优先贴这三个，都是"能直接看出水平"的：
`mcd_lunch_ci/solver.py` 的 DP、`mcd_lunch_ci/models.py` 的 `Combo.kcal_known`、
`mcd_lunch_ci/live.py` 的 `unit_prices()`（逐项核价那段）。

## 八、被问到时的标准回答（提前准备好）

**"为什么不直接让大模型推荐？"**
> 因为它给的是"看起来合理"，不是"算得最优"。而且更重要的是：过敏原不能交给概率。
> 我们这里忌口是代码里的集合交集，模型没有放行权限。

**"过敏原数据可靠吗？"**
> 不完全可靠，这一点项目里写清楚了：在线菜单不带成分表，只能按品名保守推断（宁可多标）。
> README 和报告里都标了"过敏原判断请以门店/官方成分表为准"，不越界。

**"不就是个比价脚本？"**
> 比价是单向的：同样的东西找最便宜的。这里是多目标：8 个人各有下限，
> 总预算一个上限，要最大化的是总满意度。而且会告诉你牺牲了谁、牺牲多少。
> 省钱类工具在榜上已经很多了，这个不是同一条赛道。

**"为什么还要人扫码付款？"**
> 故意的。Agent 不该碰钱。`--confirm` 是唯一的写操作入口，默认关。

**"数据是不是编的？"**
> 菜单和价格是从真实 MCP 同步的快照（`data/live_menu_snapshot.json` 里有同步时间和门店号），
> 营养是官方 `list-nutrition-foods` 的实测值，57/102 条能对上。对不上的显示"未知"，不填 0。
